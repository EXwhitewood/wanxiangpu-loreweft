# 工作流性能基线与发布门禁

## 当前结论

工作流已经持久化执行状态和步骤耗时，但现阶段只有测量基线，**尚未形成可据以批准上线的时延 SLO 阈值**。不能把单次最快结果、历史极值或主观等待感受写成阈值。

只读接口：`GET /api/workflows/performance-summary`

- `completed_samples`：目标完成样本数，最小 10、默认 20、最大 100。
- `project_id`：可选，按项目隔离候选样本。
- `trigger_type`：可选，比较同一种工作流，避免不同 DAG 混采。

接口从最新终态执行开始向前取样，直到收集到目标数量的 `completed` 执行；期间的 `failed`、`interrupted`、`partial`、`cancelled` 与 `aborted` 执行不会被丢弃，因此失败率和失败成本仍进入统计。

## 指标口径

- `total`：终态执行尝试；耗时为 `WorkflowExecution.created_at → updated_at`。
- `agents`：按 `WorkflowStep.agent_name` 聚合步骤样本。
- `stages`：按持久化的 `WorkflowStep.layer` 聚合。同层节点可能并行，阶段耗时优先使用该层最早开始到最晚结束的墙钟时间，时间戳不完整时取同层节点最大耗时，不做相加。
- 每个层级均返回 `sample_count`、`timed_sample_count`、P50、P95、失败率和状态分布；P50/P95 使用线性插值，单位为毫秒。
- 失败率只按明确失败终态计算；完整状态分布始终保留，避免把 `degraded`、`skipped` 或历史异常状态静默折算成成功/失败。

## 样本状态

- `sufficient`：已取得请求数量的完成执行；仅表示样本数量达标，不表示达到发布阈值。
- `insufficient_samples`：有数据，但完成执行少于请求数量。可以观察数据，不能据此设定或宣称 SLO 达标。
- `no_data`：没有符合筛选条件的终态执行。

## 发布门禁

在正式候选环境按相同模型、模型参数、章节规模、质量策略和工作流版本采集至少 10 个完成执行后，才允许讨论阈值。阈值应由候选样本的 P50/P95、失败率、成本和用户可接受等待共同确定，并记录基线日期、版本与筛选条件。

当前接口是测量工具，不自动批准或拒绝发布。首次阈值确定前，以下任一情况都应保持“未建立 SLO”状态：

1. `sample_status != sufficient`；
2. 混合了不同工作流类型、模型或关键质量配置，且无法分组解释；
3. 终态时间戳或步骤时间覆盖不完整；
4. 没有同时审查失败率、失败状态和恢复成本。

## 已知限制与下一轮埋点

执行表没有独立的排队、真正开始、累计暂停、人工等待和终态时间字段，因此 `total` 可能同时包含排队、暂停和人工审查等待，不能把它直接解释为纯模型推理时间。DAG layer 也不是人为命名的“规划/生成/审查/修复/提交”业务阶段。

若要建立分阶段正式 SLO，后续应持久化 `queued_at`、`started_at`、`terminal_at`、累计暂停/人工等待时长，并为步骤记录稳定的业务阶段标识和 token/模型成本；在这些字段存在前，不对缺失阶段做推断或补零。
